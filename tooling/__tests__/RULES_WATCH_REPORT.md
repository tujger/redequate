# Automatic Firebase Rules workflow: verification

The requested workflow is now connected directly in TheWhiskyTalks:

```sh
# Redequate terminal
npm run "start core"
# Application terminal
npm run start:emulator
```

No separate Rules generation or application command is needed for this workflow.
The existing application build commands generate Rules through a build-only Vite
plugin before building. Existing deployment targets are unchanged; no production
Firebase operation was run.

## Implementation

- `tooling/firebase-rules.mjs`: fresh base JSON reads on every composition;
  unchanged-output suppression; `watchRules(configFile)` with dependency polling,
  debounce, atomic-save support, missing-import recovery and explicit close;
  `firebaseRulesBuildPlugin(configFile)`; isolated `buildRules(configFile, {output})`.
- TheWhiskyTalks: database manifest, generated Firebase config path, generation
  before developer Emulator startup, watcher managed by the launcher finally,
  isolated generation for test:emulator, and a Vite build hook.
- Application base copy removed after structural equality verification. Generated
  `.firebase/generated/` output is ignored. Runtime provider choices and App.js
  were not changed by this task.
- Source resolution is tracked again after changes. Failure keeps previous output;
  changing the output location requires restart. Firebase CLI owns compilation and
  live application, logging `Rules updated.` after acceptance.
- A compiler-invalid expression can be generated as JSON; Firebase rejects it and
  retains the last accepted Rules until correction. A generated-file message does
  not claim successful compilation.
- Demo repository was not modified. The obsolete TheWhiskyTalks migration patch
  was removed; demo migration materials remain unapplied.

The live hot-reload test is `firebase-rules-watch.emulator.mjs` beside this report.
It ran against a separate demo project and disposable base/provider copies. It
confirmed actual REST behavior after base edits, inline and imported additions,
index updates and validation updates; preservation after invalid JSON; compiler
rejection of an invalid expression; recovery after correction. The Database
Emulator PID was unchanged throughout. It verified port release and removed its
private temporary directory.

Application suite failures:

1. `Activity indexes original types as record values and merges concurrent events`:
   expected undefined but read `{legacy: 1}`.
2. `native increment markers pass through the callable as atomic writes`:
   functions/invalid-argument, `Record update failed. [400]`.

The task did not modify backend algorithms. Generated Rules are identical to the
original application Rules, so these failures do not demonstrate a permission
change. The full application suite is nevertheless not claimed green. No unrelated
backend/test expectations were rewritten to make it pass.

The application suite used `demo-thewhiskytalks-test`, private TMPDIR/TMP/TEMP and
ports 19099, 19000, 15001, 19199, 14400, 14500, 19299, 19499 (UI disabled). All of
those ports, plus the configured unused UI port 14000, were rebound successfully
after graceful shutdown. No developer snapshot was imported or exported.
Functions archive and lockfile regenerated by its prepare step were restored to
their exact pre-test bytes. Developer processes were not stopped.
