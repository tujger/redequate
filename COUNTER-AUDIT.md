# Проверка счетчиков — 24 октября 2026

**Критерий «все сценарии работают» не выполнен.** Воспроизведены ошибки арифметики,
управления подписками и отображения уведомлений. Для Local выявлены ограничения
совместимости путей и отсутствие серверной агрегации. Исправления рабочего кода
не входят в этот аудит: добавлены тесты, тестовые fixtures, запуск эмулятора и отчет.
Сравнение с исторической версией не выполнялось; дата появления ошибок не установлена.

## Среда и способ проверки

Проверены текущие рабочие деревья `redequate` и `thewhiskytalks`, ветка `master`.
Local использует настоящий код IndexedDB-провайдера с `fake-indexeddb`; Firebase —
настоящий RTDB SDK и локальный Database Emulator проекта `demo-redequate-tests`.
DOM проверяется через React 19 `createRoot`/`act` в jsdom. Замокан только выбор
провайдера через hook; операции БД и доставка событий в этих тестах реальные.
Пять секунд в компоненте The Whisky Talks проверяются виртуальными таймерами.

Проверены значения после записи, повторное чтение, начальный снимок, события из
второго экземпляра провайдера, изоляция соседних счетчиков, отписка, смена пути,
размонтирование, StrictMode и конкурирующие изменения: 20 увеличений и 12 уменьшений
дают 8 без потерянных записей. Ветви `increase`, знакового `increment`, `decrease`,
`value`, чтения и наблюдения проверены для отсутствующего, нулевого, положительного
и старого отрицательного значения. При совместном указании наблюдателя и операции
подтвержден существующий приоритет наблюдения.

## Подтвержденные проблемы и ограничения

| ID | Где | Ожидание → фактический результат |
| --- | --- | --- |
| C1 | `counterControl`, оба провайдера | `increment: -2` от отсутствующего, нулевого или отрицательного значения должен оставить счетчик пустым; возвращается и сохраняется `-2`. |
| C2 | `counterControl`, оба провайдера | `value: 0` должен сбросить положительный счетчик; старое значение сохраняется. Влияет на восстановление лайков, когда extras больше нет. |
| C3 | Библиотечный `CounterComponent`, оба провайдера | Смена только `live` при стабильном `path` не запускает и не останавливает подписку. Проверяется без `counter`, поскольку `counter` вместе с `path` уже включает наблюдение по существующему контракту. |
| C4 | Библиотечный `CounterComponent`, оба провайдера | При замене объекта `database` и стабильных остальных props подписка остается на прежнем провайдере. |
| C5 | Библиотечный `CounterComponent`, оба провайдера | После замены только `onChange` события продолжают поступать старому обработчику. |
| C6 | Совместимость путей Local | Строка `user/mutual/friend` и массив строк `[post, replied]` работают в Firebase, но запись скалярного счетчика в Local отклоняется: `A collection value must be a record object or null`. Проверенные рабочие формы Local используют именованный сегмент идентификатора. |
| C7 | Local, путь запросов из `MutualComponent` | Для `[{id: user}, "mutualrequests", {typeId: "friend", _: true}]` подписчик получает начальный `undefined`, но после увеличения не получает `2`. В Firebase тот же сценарий проходит. |
| C8 | Ограничение Local пользовательских сценариев | Добавление like/dislike, публикация поста, создание following и friend request сохраняют исходную запись, но не увеличивают соответствующий `_counters`. Реакция меняет счетчик в памяти `PostData`. Local backend документирован как симуляция и не воспроизводит Cloud Functions; равенство возможностей с Firebase этим не обеспечено. |
| C9 | `thewhiskytalks/src/components/CounterComponent.js`, оба провайдера | При `initialValue=2`, первом снимке `2` и следующем значении `3` вызывается `onChange(3)`, но `children` с уведомлением остаются скрытыми. При начальном снимке, отличном от `initialValue`, последующее изменение показывает уведомление. |
| C10 | `thewhiskytalks/functions/fixes/user.js` | `fixUserPostCounters` создает `Pagination`, но не вызывает `next()`: публикации и ответы обнуляются, ошибка чтения не возникает. Это подтверждают четыре уже существовавших теста: обычный пересчет, migrated reply, ошибка чтения и 100001 запись. |

Причина C1/C2 — ранние возвраты и проверки чисел на truthiness в
`src/controllers/counterControl.js:28`. Причина C3–C5 — зависимости эффекта
`[path, counter]` в `src/components/CounterComponent.js:25`. Условие, скрывающее
первое уведомление C9, находится в соседнем приложении в
`src/components/CounterComponent.js:37`. C10 — участок после создания пагинации,
`functions/fixes/user.js:99`.

## Что работает и кто пишет счетчики

| Сценарий | Проверенный результат |
| --- | --- |
| Именованные пути постов, followers/following и профиля | Чтение, положительные изменения, уменьшение до удаления и события проходят на обоих провайдерах; исключение C7 указано отдельно. |
| Обычная подписка библиотечного UI | DOM меняется вслед за реальными записями; смена пути, отписка, размонтирование и StrictMode проходят. |
| Числовой счетчик приложения | Без `initialValue` применяется нулевая задержка; при положительном `initialValue` сохраняется debounce 5000 мс, показывается последнее значение, включая ноль. Старый таймер отменяется при смене пути и размонтировании. |
| Уведомление через `children` | Нулевая задержка и доставка `onChange` работают; исключение первого изменения C9 воспроизводится отдельно. |
| Реакции | Клиентский `PostData.putExtra/removeExtra` меняет extra и память; Functions `extraCreated/extraDeleted` увеличивают/уменьшают сохраненный like/dislike. Обе серверные пары проходят тесты. |
| Following, friend, watching | Functions `mutualCreated/mutualDeleted` меняют счетчики обоих направлений и удаляют нулевые значения. Все три типа проходят. |
| Запросы дружбы | `mutualRequestCreated` увеличивает pending; `mutualAction` при accept/reject уменьшает pending. Для accept отдельно вызваны реальные обработчики созданных двух связей и проверены четыре направленных счетчика. |
| Посты и ответы | Создание/удаление корневого поста симметрично меняет total и author/posts; прямой и вложенный ответ меняют writer/replies и root/replied. |
| Ленты mutualstamps | Проверены общая авторская запись `_my` для following/friend и защита watching от повторного события. Это не доказательство идемпотентности всех серверных триггеров. |

Серверные тесты вызывают реальные экспортированные обработчики через `.run()` с
существующим in-memory Admin SDK fixture. Автоматическая диспетчеризация событий
Functions Emulator, реальные сетевые задержки и порядок облачных триггеров не проверялись.
Эмуляторные тесты клиентского провайдера проверяют доставку уже записанного счетчика.
Физические браузеры, Android и production Firebase не запускались.

В demo-приложении используются общие компоненты Redequate; отдельного писателя
`_counters` в просмотренном demo-коде не найдено. Совместимость общих компонентов
покрыта библиотечными тестами; отдельный браузерный smoke demo не выполнялся.

## Повторение

Из каталога Redequate:

```sh
npm run test:unit
npm run test:integration
COUNTER_AUDIT_STRICT=1 npm run test:unit -- src/__tests__/controllers/counterControl.audit.test.js src/__tests__/components/CounterComponent.audit.test.js src/__tests__/components/PostComponent/localCounterWriters.audit.test.js
COUNTER_AUDIT_STRICT=1 npm run test:integration
```

Из каталога The Whisky Talks:

```sh
npm test -- src/__tests__/CounterComponent.test.js src/__tests__/CounterComponent.providers.test.js src/__tests__/Profile.test.js
npm run test:counter:integration
COUNTER_AUDIT_STRICT=1 npm run test:counter:integration
npm --prefix functions test
```

Новый `test:counter:integration` использует Firebase CLI связанного Redequate,
создает временную конфигурацию с доступом только к тестовым `_counters`, запускает
только Database Emulator на `127.0.0.1:9000` и завершает его после тестов.
Нужна Java 21; на этом Mac используется уже установленный Temurin из окружения
Redequate. Настройки production и deployment не изменяются. Для unit-тестов
приложению добавлена dev-зависимость `fake-indexeddb`.

Критерий приемки для следующего шага: устранить или явно согласовать ограничения
C1–C10, перевести соответствующие ожидаемые падения в обычные тесты и получить
успешный строгий прогон. Исправление независимых падений общего набора необходимо
для общего зеленого статуса репозиториев.
